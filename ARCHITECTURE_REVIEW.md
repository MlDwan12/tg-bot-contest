> факты, выводы, открытые вопросы и принятые решения. В конце соберём итоговую картину.

**Проект:** Telegram Contest Bot — система управления конкурсами в Telegram-каналах стримеров.
**Формат:** внутренний сервис. Операторы (сотрудники) заводят конкурсы для стримеров, к которым в группу добавлен бот с полными правами.
**Команда:** 1 бекенд-разработчик + 1 фронтенд. Bus factor = 1. → простота = требование надёжности, не эстетика.
**Стек:** NestJS 11, PostgreSQL + TypeORM, BullMQ + Redis, Telegraf, JWT, стек мониторинга (Prometheus/Loki/Grafana/Promtail), Sentry.

**Легенда критичности:** 🔴 решать сейчас · 🟡 следить/заложить · 🟢 ок / преждевременно.

## Цель и принципы разбора
- **Цель:** надёжность + читаемость + поддерживаемость силами одного бекенд-разработчика.
- **Архитектурный подход (РЕШЕНО):** модульный монолит (макро) + **прагматичный слоёный** `Controller→Service→Repository`, один репозиторий на агрегат (микро). Порты только на внешний I/O (Telegram). Отвергнуты Clean/Hexagonal и DDD+CQRS как удвоение церемонии. Детали → [PROJECT_STRUCTURE.md](./PROJECT_STRUCTURE.md).
- **Путь: эволюционный (strangler / incremental), НЕ переписывание с нуля.** Обоснование: bus factor = 1, тестов почти нет, система работает; в коде закодированы дорогие знания о крайних случаях (advisory lock, перехват `23505`, atomic claim публикаций, grace-period). Rewrite теряет страховку и ведёт в ловушку паритета/second-system.
- **Порядок работ (после аналитики Q4–Q6):** сначала тесты на критические потоки (участие/завершение/розыгрыш) → затем резать по одному шву, каждый шаг откатываем.
- **Метод разбора:** блок за блоком, вопросы → карта проблем → приоритизированный план. Сначала «что не так», потом «как чинить».

## Q1 — Бизнес-задача и масштаб ✅

### Факты (со слов + из кода)
- Внутренний инструмент. «Клиенты» — стримеры; к их группе подключают бота с полными правами.
- **Число стримеров — не фиксированное, растущее, с оттоком** (приходят постоянно, кто-то уходит). По сути — растущая мини-платформа с внутренними операторами.
- Крупнейший стример: **~50 000 подписчиков**.
- Конверсия в участие: **~40%** (грубо) → до **~20 000 участников** на конкурс.
- Сейчас: **1 активный конкурс на группу**; в перспективе заложить возможность нескольких.
- **Уведомления победителям НЕ рассылаются** — модель **pull**: пользователь сам жмёт кнопку и смотрит победителей.
- На завершении уходит уведомление только **админам** (единицы): кто победил, в какой группе, каком конкурсе.
- Массовая рассылка (`/users/broadcast`, очередь `user-mailing`) — **отдельная ручная фича**, не привязана к завершению конкурса.

### Оценка нагрузки (пик)
| Путь | Нагрузка | Оценка |
|------|----------|--------|
| Запись участий | ~20k INSERT, размазаны по времени, пик — десятки/сек | 🟢 БД не замечает |
| Уведомление админам на завершении | 3–5 сообщений | 🟢 Ничто |
| Просмотр победителей (pull) | до 20k нажатий → чтения из БД, всплеск после завершения | 🟡 Дёшево; первый кандидат на кэш при росте |
| Массовая рассылка | тяжёлый исходящий фан-аут, но только по ручному запуску | 🟢 Уже в BullMQ + bottleneck |

### Выводы / решения
- 🟢 **По нагрузке проект в лёгкой категории и надолго.** Инфраструктурного потолка в ближайший год не будет.
- 🟢 **Число стримеров нагрузки не создаёт** — её задаёт размер крупнейшего в момент старта. Он демпфирован pull-моделью.
- 🟢 **Самый тяжёлый исходящий путь (рассылка) уже правильно вынесен в очередь** — не в синхронный HTTP.
- 🟡 **Всплеск чтений при просмотре победителей** — не проблема сейчас, первый кандидат на кэш, если конверсия/аудитория вырастут.
- ➡️ Будущие риски лежат **не в нагрузке, а в корректности и поддерживаемости**: гонки при 20k участиях, честность выбора победителя, связность модулей, отсутствие tenant/owner-слоя при росте числа стримеров.

### Открытые вопросы (вернуться позже)
- **Нет tenant/owner-модели:** `Channel` без владельца, `Contest.creator` — это оператор, а не стример. Все каналы/конкурсы в общем пуле. Терпимо сейчас; при сотнях стримеров с текучкой начнёт мешать (изоляция, атрибуция, чистка ушедших). → обсудить в Q3/Q6.

## Q2 — Пользовательские сценарии (участие / выбор победителя / завершение) 🔄

Разобраны три горячих потока по коду. Участие приходит через публичный REST `POST /contest/:id/participate` (бот-`Update` — заглушка; кнопка в посте открывает web-app, который бьёт в API).

### Общая оценка
Concurrency-гигиена **выше среднего**: advisory lock, атомарные CAS-гварды статуса, идемпотентный перехват дублей, atomic claim публикаций. Ниже — что реально требует внимания.

### Находки (по приоритету)

**🔴 F1 — Гонка при завершении: победитель может «перевыбраться».**
Два входа в завершение, защищён только один:
- `finishContestIdempotent` (шедулер) — берёт `pg_try_advisory_lock`. ✅
- `completeContest` (ручной `PATCH /:id/complete`) — **лока не берёт**, статус меняет неатомарно (`if status===COMPLETED throw` … потом `update`).
Между проверкой и записью — TOCTOU. Двойной клик/ретрай админа на медленном (20k участников) запросе → два независимых `Math.random()`-розыгрыша → второй `replace` перезаписывает первого. Advisory lock шедулера против ручного пути бесполезен.
- Критичность: высокая по последствиям (честность призов = суть продукта), средняя по вероятности.
- Укусит: уже, на любом ручном завершении.
- **Решение сейчас (дёшево):** атомарный «gate» перед розыгрышем — либо тот же advisory lock в `completeContest`, либо `updateStatusIfNotCompleted` как ворота (кто перевёл статус — тот и разыгрывает).

**🟡 F2 — Проверка `requiredChannels` = синхронный Telegram-вызов в горячем пути участия.**
`checkUserInChannels` (getChatMember) на каждого участника. На пиковом старте 50k-стримера — тысячи вызовов Telegram API/мин, rate-limited → ложные отказы + латентность. Единственная внешняя зависимость на горячем пути.
- Укусит: пиковый старт крупного стримера с обязательными каналами.
- Отложить: кэш членства `(user, channel)` TTL 30–60с.

**🟡 F3 — Честность рандома: `Math.random()`.**
Розыгрыш не крипто-стойкий, не воспроизводимый, не аудируемый. Для ценных призов нечем доказать честность.
- Решение — осознанный выбор по ценности приза (вопрос открыт). Для ценных: `crypto.randomInt` + сохранять seed/лог розыгрыша.

**🟡 F4 — Розыгрыш/завершение грузят всех участников в память по нескольку раз.**
`resolveAutomaticWinners` тянет 20k участников+юзеров в JS ради выбора N. `completeContest` за вызов грузит полный набор **трижды**. Дедуп в памяти избыточен (уникальный индекс уже гарантирует).
- Укусит: ~100k+ участников / память воркера.
- Отложить: `ORDER BY random() LIMIT n` в SQL.

**⚪ F5 (минор) — MANUAL grace-period.** При отсутствии выбранного победителя `endDate` сдвигается на +2ч и админам шлётся уведомление **на каждой** ретрай-попытке → потенциально бесконечное продление + спам админам, если победителя так и не выбрали.

### 🟢 Сделано правильно (не трогать)
Дубли участия (уникальный индекс + перехват `23505` → идемпотентный 200); pull-модель победителей (нет фан-аута); advisory lock в шедулере; атомарные `updateStatusIfCurrent/IfNotCompleted`; atomic claim публикаций + stale-requeue; `requiredChannels` реально грузится (гейт не обходится).

### Открытые вопросы
- Ценность призов? (определяет, нужен ли крипто-рандом + аудит розыгрыша — F3)
- Публичный `participate` без аутентификации: валидируется ли Telegram `initData` (HMAC), или `telegramId` принимается на доверии от клиента? → потенциальная накрутка участия. Обсудить в Q5 (security).

### Решения по Q2
- 🔴 **Принято к исполнению сейчас:** закрыть F1 (атомарный gate в `completeContest`). Остальное (F2–F5) — в план, не сейчас.

## Q3 — Текущая архитектура (связность, слои, паттерны) 🔄

Граф зависимостей собран из всех `*.module.ts`.

### Q3.1 🔴 Модули связаны в клубок через `forwardRef` (циклические зависимости)
**Граф (⇄ = взаимный цикл):**
```
Bot ⇄ Contests ⇄ Users ⇄ Bot     (тройной цикл)
Bot ⇄ Channels ,  Contests ⇄ Channels
Users ⇄ Auth ,  Channels ⇄ Auth
```
10 `forwardRef` на уровне модулей + внутри сервисов (`ContestsParticipateService`: `forwardRef(TelegramUserService/TelegramService)`, `contest-participate.service.ts:48-51`). `Bot/Contests/Users/Channels` взаимно переплетены — это монолитный клубок, а не модульная архитектура.
- **Механизм проблемы:** `forwardRef` не убирает цикл, а откладывает резолв. Нет направления зависимостей (нет ядра/периферии); хрупкая инициализация (риск `undefined` deps); нельзя тестировать/поднимать/выносить модули изолированно.
- **Корневая причина:** `TelegramService` — низкоуровневый транспорт, нужный всем, но лежит в `BotModule`, который зависит обратно на домен → почти все циклы отсюда.
- **Высоколевериджный шаг (обсуждён, не делаем):** вынести листовой `TelegramTransportModule` (только `sendMessage/getChatMember/editMessage`, без доменных зависимостей). Одним движением рвутся 3 цикла (`Bot⇄Contests/Channels/Users`). Останется разобрать `Contests⇄Users`.
- Критичность: средняя сейчас (работает), но налог на каждое изменение + блокер для любого будущего разделения (Q6).
- Сейчас/потом: распил — **потом, планово**. **Сейчас — правило:** новые связи не через `forwardRef`, а через листовые модули/события.

### Q3.2 🟡 CQRS-lite (read/write репозитории + интерфейсы-токены) — церемония без окупаемости
6 репозиториев + 6 интерфейсов + 6 токенов только на агрегат «контест» (`contests.module.ts:64-93`).
- Раздельные read/write оправданы при: (1) расходящихся read/write-моделях — **нет** (те же сущности); (2) раздельном масштабировании чтения — **нет** по Q1; (3) командной дисциплине — зависит от команды (открыто).
- **Ключевой довод против: абстракция дырявая.** Сервисы импортируют репозитории то через `../interfaces`, то напрямую конкретный класс из `../repositories` (напр. `contest-winner.service.ts`). Цену церемонии платите, выгоды развязки (подмена в тестах/смена хранилища) не получаете.
- Критичность: низкая (не баг), но постоянный налог на скорость разработки.
- Сейчас/потом: **не расширять**; при трении — схлопнуть per-aggregate read+write в один репозиторий. Прямо зависит от размера команды (открытый вопрос).

### Q3.3 🟡 «Толстые» сервисы и god-модуль конкурсов
`ContestsParticipateService` — 8 зависимостей (2 `forwardRef`), метод `participate()` совмещает 5 ответственностей (валидация статуса, upsert юзера, внешний Telegram-вызов подписки, запись участия, постановка джоба, чтение победителей в ветке COMPLETED). `ContestsModule` = 6 сервисов + 6 репо + процессоры — центр тяжести системы.
- Критичность: низкая-средняя. Укусит при добавлении новых типов конкурсов/условий участия.
- Потом: выделить условия участия в цепочку правил.

### Q3.4 🟡 Непоследовательная дисциплина rate-limit к Telegram
Часть исходящих идёт через очередь + `bottleneck` (рассылка — правильно), часть — синхронно мимо очереди (проверка подписки в `participate` = F2; уведомления админам циклом `for` в `contest-lifecycle`). Единой точки соблюдения лимитов нет. Следствие Q3.1 — единый листовой транспорт с общим лимитером решил бы и это.

### Q3.5 ⚪ Гигиена репозитория (не архитектура)
В корне два `.tar` по ~252 МБ + закоммиченный `dist/`. Проверить `.gitignore` — дампы образов не место в VCS.

### Закрытый вопрос: команда = 1 бекендер + 1 фронтендер
**Сквозной вывод:** архитектура написана под команду 5–10 человек с bounded-контекстами, а тянет её один бекендер. Код несёт координационные издержки большой команды без её выгод. Главный архитектурный риск проекта — **не нагрузка (Q1 показал запас) и не отдельные баги, а несоответствие сложности архитектуры размеру команды.** Стратегия на 6–12 мес: не добавлять слои, а осознанно упрощать в сторону «умещается в одну голову».

### Решения по Q3 (с учётом команды)
- 🔴 **Q3.2 — вердикт: для команды из 1 бекендера CQRS-lite = чистый балласт.** Выгоды (владение частями, подмена реализаций, границы) требуют команды; соло получает только налог + рост bus-factor-риска. **Решение: не расширять; при касании агрегата — эволюционно схлопывать read+write в один репозиторий на агрегат.** Big-bang выпил НЕ делать (churn на непокрытом тестами коде).
- 🔴 Q3.1 — распил циклов через листовой `TelegramTransportModule`: **в план (не сейчас)**; сейчас — правило «без новых `forwardRef`». Для соло ценность выше (кодовая база в одну голову).
- 🟡 Q3.3 — дробление `participate()` на правила: планово, окупается у соло.
- 🟡 Q3.4 — единая точка rate-limit — побочный выигрыш от Q3.1.

## Q4 — Технологии ✅

Проверено grep'ами + `main.ts`. Тяжёлой архитектуры нет; есть лишний вес и полу-провода, дающие ложную безопасность (для соло опаснее, чем для команды).

### Q4.1 🟡 Мёртвый второй ORM — `mongoose`
`mongoose@9` + `@nestjs/mongoose@11` в deps, использований в `src` — ноль. README = Postgres only. Ложный сигнал будущему читателю + вес. Удаление — нулевой риск.

### Q4.2 🟡 Две bcrypt-библиотеки в одном auth-флоу (латентный риск)
`user-admin.service.ts` хэширует через `bcryptjs`; `auth.service.ts` проверяет через нативный `bcrypt`. Формат `$2` обычно кросс-совместим (вряд ли активный баг), но аутентификация держится на совместимости двух реализаций + нативный `bcrypt` требует node-gyp (риск деплоя). **Решение:** оставить одну (рекомендую `bcryptjs` — чистый JS, скорость на логине админа не важна); проверить верифицируемость существующих хэшей.

### Q4.3 🟡 Sentry полу-подключён → ложное «ошибки под контролем»
(1) `@sentry/tracing@7` — мёртвая+устаревшая зависимость (слита в `@sentry/node@10`), не импортируется → удалить. (2) `Sentry.init()` в конце bootstrap (`main.ts:132`), должен быть первым. (3) `SentryFilter` закомментирован (`main.ts:108`) — необработанные HTTP-ошибки, вероятно, не долетают; ловятся только события очередей + ручное. **Решение:** довести (init первым + отправка из `AllExceptionsFilter`) или честно выпилить. Для соло рабочий Sentry = вторая пара глаз.

### Q4.4 🟢→🟡 Очереди: 6 живых оправданы, 1 мёртвая
6 процессоров (`scheduler/finish/publication/maintenance/counters/user-mailing`) — разные нагрузки с разными ретраями, over-engineering нет 🟢. Но `telegram-messages` зарегистрирована + в Bull Board + health-check, но **без процессора и продюсеров** — брошенный каркас единой очереди-воронки Telegram (= Q3.4). Варианты: (а) удалить, (б) **воскресить как единый канал отправки** (закроет Q3.4, обвязка уже есть) — склоняюсь к (б), позже.

### Q4.5 ⚪ Config-запахи (бьют соло-мейнтейнера)
- CORS-домены захардкожены в `main.ts:114` → в env.
- Порт по умолчанию `3000` в коде/логах (`main.ts:136,141`) vs реальный 3004 — дезинформация.
- `jsonwebtoken` импортируется напрямую (`main.ts:18`), в deps его нет — транзитивный, сломается при апгрейде `@nestjs/jwt`.
- `helmet()` (`main.ts:99`) подключён ПОСЛЕ роутера Bull Board (`main.ts:98`) — не покрывает `/admin/queues`.

### 🟢 Хорошо
Ручная JWT-защита Bull Board на уровне Express; `ValidationPipe` с `whitelist + forbidNonWhitelisted + transform`.

### Решения по Q4 (лёгкие безопасные шаги — кандидаты в «быстрые победы»)
- 🟡 Удалить мёртвое: `mongoose`, `@nestjs/mongoose`, `@sentry/tracing`. Нулевой риск.
- 🟡 Консолидировать bcrypt → одна библиотека (проверить хэши).
- 🟡 Sentry: довести или выпилить (не оставлять полу-состояние).
- 🟡 `telegram-messages`: решить (а) удалить / (б) воскресить как воронку Telegram (связано с Q3.4).
- ⚪ Config: вынести CORS/порт в env; починить порядок `helmet`; добавить `jsonwebtoken` в deps явно (или использовать `@nestjs/jwt`).

## Q5 — Что болит сейчас 🔄

### Контекст рисков (уточнено)
- **Ценность приза: от 100 ₽ до 10 000 000 ₽** (до ~$120k за розыгрыш). Риск сидит в дорогом «хвосте».
- Победитель вручается **вручную** (операторы связываются) → собрать приз может только владелец аккаунта.
- Число участников **отображается на кнопке участия** (публичный счётчик).
- **Две стратегии выбора победителя: RANDOM (жребий) и MANUAL (операторы назначают).** Стратегия радикально меняет threat-модель.

### Q5.1 🔴 (RANDOM+дорогой = 🔴🔴) Участие полностью подделываемо — нет аутентификации `initData`
`POST /contest/:id/participate` — публичный, без guard, без throttler; `telegramId` берётся из тела (`@IsString()`), нигде не валидируется Telegram `initData` (grep пустой). `ensureUser` заводит юзера под любой id. Проверка `requiredChannels` (getChatMember) — это **авторизация** («член ли канала»), а НЕ **аутентификация** («ты ли это»): она условна (нет required channels → 0 защиты), а `telegramId` членов не секрет (утекают через форварды/метаданные), + сообщение об ошибке работает оракулом членства.

**Payoff по стратегии:**
| Мотив | RANDOM | MANUAL |
|---|---|---|
| Победа через свои sockpuppet-аккаунты | 🔴 живёт (при 10М — рационально) | 🟢 мёртв (исход у людей) |
| Саботаж (фейк побеждает → конкурс сломан) | 🔴 живёт | 🟢 фейк не выберут; но список замусорен |
| Инфляция публичного счётчика | 🟡 живёт | 🟡 живёт |

**Фикс (фундамент, универсальный):** валидировать `initData` (HMAC-SHA256 по токену бота), брать `telegramId` из проверенной подписи, игнорировать тело. От этого зависит всё остальное (честный жребий, достоверный счётчик, чистый список). Приоритет №0.

### Q5.2 🔴 (при дорогих призах) MANUAL: честность держится только на честности оператора, нет аудит-следа
В MANUAL исход назначают операторы → техгарантии честности нет by design. При 10М ₽ — инсайдерский риск (оператор назначает сообщника) и **нечем доказать легитимность** в споре. Нужен неизменяемый аудит-лог: кто/когда/какого победителя назначил. Плюс вопрос disclosure (аудитории конкурс подаётся как «розыгрыш»?). Защищает в первую очередь самих операторов.

### F3 эскалирована 🟡→🔴 (для RANDOM+дорогой)
`Math.random()` при розыгрыше на миллионы недопустим: не крипто-стойкий И не аудируемый. Нужно `crypto.randomInt` + сохранённый след розыгрыша (seed/входные данные) для доказуемости.

### Архитектурный принцип (для плана)
Система обрабатывает конкурс за 100 ₽ и за 10М ₽ одинаково, а риск — в хвосте. `initData` — универсальный фундамент (обе стратегии, любая цена). Крипто-рандом + аудит MANUAL можно вводить **тиром по цене приза**; для соло проще единый путь — взвесить «тир vs одинаково» на этапе плана.

### Реальные инциденты в проде (подтверждают находки)
- **Инцидент №1 = F1 (наблюдался):** при авто-завершении конкурса с выбранным победителем победитель перевыбирался на другого.
  - **Починено частично** (коммит `05ab97a`): в `resolveAndSaveWinners` добавлен guard `if existingWinners.length>0 → reuse`. Симптом «перевыбор уже выбранного» закрыт для последовательного случая.
  - **Осталось открытым:** `completeContest` по-прежнему БЕЗ advisory lock и пишет статус неатомарно (`update({status})`, не `updateStatusIfNotCompleted`). Reuse-guard = read-then-write без блокировки (TOCTOU). **Residual race:** RANDOM-конкурс без заранее выбранного победителя + два одновременных завершения (двойной клик / ручное впритык к шедулеру) → два разных `Math.random`-розыгрыша. При 10М ₽ — катастрофа. **Настоящий фикс:** advisory lock / атомарные ворота в `completeContest`. → F1 НЕ снят.
- **Инцидент №2 = F5 → переклассифицирован:** grace-period (оповещение админам + сдвиг `endDate` +2ч) добавлен **намеренно** как safety-net, чтобы MANUAL-конкурс не завершился без выбранного победителя. **Это не дефект, а осознанная фича.** Остаётся один открытый дизайн-вопрос (см. ниже), напрямую связанный с целью set-and-forget.

### Цели проекта (North Star, вход в Q6)
1. **Set-and-forget надёжность** («раз запустить и забыть») → закрыть F1 до конца, ограничить F5, авто-восстановление воркеров/джоб, `initData` (чтобы не разгребать мусорные данные).
2. **Внедрение аудита** → аудит-лог назначения победителя MANUAL (Q5.2) + след розыгрыша RANDOM (F3). Пользователь пришёл к этому независимо.

### Решения по Q5
- 🔴 Q5.1 — `initData`-аутентификация участия: приоритет №0 (фундамент). RANDOM+дорогой = 🔴🔴.
- 🔴 F1 — НЕ закрыт полностью; добить advisory lock/атомарные ворота в `completeContest`.
- 🔴 Q5.2 — аудит-лог MANUAL-назначения (совпадает с целью «аудит»).
- 🔴 F3 — крипто-рандом + след розыгрыша для дорогих RANDOM.
- 🟢 F5 — **закрыто. Намеренная фича, менять логику не требуется.** Выбор победителя — ответственность человека, система корректно не берёт её на себя (авто-выбор для MANUAL был бы неверен). Единственная опциональная идея под set-and-forget: терминальное/видимое состояние для *брошенного* конкурса (после N напоминаний → заморозить + показать в ops-виде/эскалировать — **не** авто-выбор победителя), чтобы конкурс не полз в лимбе незаметно. Это **продуктовое решение на усмотрение пользователя**, кладём в «потом», низкий приоритет. Не архитектурный дефект.

# ★ ИТОГОВАЯ ПРИОРИТИЗИРОВАННАЯ КАРТИНА

## Технические предпосылки плана (подтверждено скриншотами + ответами)
- **Клиент участия = Telegram Mini App (WebApp).** `initData` доступен → фикс №1 (валидация HMAC, `telegramId` из подписи) реализуем без костылей. Подтверждено скрином Mini App «Список победителей».
- **Прод live с реальными деньгами СЕЙЧАС.** Пример: розыгрыш 10 000 ₽ («карта или USDT»). Дорогой хвост — не гипотеза. `initData`-дыра и residual F1 открыты в бою → срочность пунктов 1–2 максимальная.
- **Условия участия частично не проверяются** (лайк/коммент на YouTube — honor-system; только подписка на канал верифицируется через `getChatMember`). Честность держится на identity → `initData` критичнее.
- **Топология: один процесс** (`docker-compose`: единственный `api`, BullMQ в том же процессе, без реплик/воркера). F1-гонка реальна через async-интерливинг, но достаточно in-process/атомарного DB-гейта; тяжёлый advisory lock не обязателен. `restart: always` + резюме джоб = плюс к set-and-forget.
- **База плана = ветка `refactor`** (= чистая точка от текущего прода, изменений ещё нет; полу-фикс F1 `05ab97a` уже в проде). `master` устарел, игнорируем.
- **Операторы: 1–2, у каждого свой аккаунт** → аудит-лог назначения победителя (Q5.2) оправдан.
- **Интеграционные тесты против реальных PG+Redis — согласованы** → ⓿ выполним (юнит-моки F1/локи/уникальные индексы не ловят).
